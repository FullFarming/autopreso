# 역할별 운영 흐름과 언어·요약 안정성 개선

2026-09-05. 사용자 요청에 따라 운영자 콘솔은 별도 설계로 분석하며, 전체 신규 구축·배포는 하지 않는다. 이번 코드 변경은 확인된 언어 안정성 및 요약 대기 결함에 한정한다.

## 역할별 제품 구성

| 역할 | 해야 할 일 | 기본 화면 | 범위와 제한 |
| --- | --- | --- | --- |
| 운영자·개발사 | 회원 승인/정지, 라이선스·엔진 배정, 이용량·장애·지원 관리 | 별도 운영 콘솔 + 호스트 작업 공간 전환 | 호스트 기능 전체 사용. 다른 고객 회의 지원은 명시적인 대상 선택과 권한·감사 기록을 통해 제공 |
| 호스트·라이선스 이용자 | 캡션 준비/실행, 회의 예약/QR 공유, 발언자 관리, 언어·용어집·화면 설정, 기록 관리 | 캡션 / Live Call / 설정 | 자신의 회의·기기 설정 중심. 개발사 회원관리·다른 고객 데이터는 미노출 |
| 참여자·일회성 방문자 | 간략 정보와 동의, 시작 대기, 번역 보기, 허용된 발언 요청, 종료 후 원문·요약 | 입장 → 대기 → 라이브 → 종료 기록 | 회원가입·제품 라이선스 불필요. 해당 회의 참여 권한만 부여 |

역할(role), 계정 상태(status), 라이선스(entitlement), 회의별 권한(session grant)을 별도로 판단한다. 예를 들어 approved host라는 사실만으로 유효한 라이선스가 있다고 가정하지 않는다.

## 현재 구현에서 확인한 간극

- `webapp/app/console/`에는 사용자·세션·엔진 화면이 있고 서버에서 admin+approved를 검사한다. 운영자 화면을 처음부터 다시 만들기보다 이 콘솔을 별도 제품 영역으로 발전시키는 편이 적합하다.
- 일반 호스트 API는 hostId 소유 조건을 사용한다. 현재 admin이라고 타 고객 회의를 자동으로 볼 수 있는 구조는 아니다. 전체 데이터 접근이 구현됐다고 볼 수 없다.
- 회의 생성 시 유효 기간·좌석·동시 연결 수 등을 묶은 독립 라이선스 검사가 부족하다. 라이선스 모델과 갱신 정책을 별도 작업으로 추가해야 한다.
- 캡션과 Live Call은 서로 다른 실행 경로가 있다. 하나만 수정하면 같은 문제가 다른 화면에 남는다.

## 참여 흐름에서 추가로 확인된 차이

| 우선순위 | 현재 상태 | 권고 |
| --- | --- | --- |
| P1 | 요약 이메일 수신 신청만 저장하며 실제 발송 구현은 없음 (`ViewerRecapRequest.tsx`) | 요약 완료→동의 확인→발송 작업 큐→중복 방지·실패 재시도·발송 이력 설계. 이번 작업에서 실제 발송하지 않음 |
| P1 | 이름과 이메일 모두 입장 필수 | 최소 정보 입장을 원하면 이름 필수/이메일은 수신 동의 시 필수로 데이터 검증과 UI를 함께 변경 |
| P2 | 일반 공유 링크에 `#code=`가 있어 코드가 미리 채워짐 | 사용자가 직접 입력하는 일반 주소와 코드 포함 편의 공유를 명확히 구분. 기존 공유의 작동을 예고 없이 바꾸지 않음 |
| P2 | 종료 기록 접근은 종료 후6시간으로 제한 | 참여자에게 접근 가능 기간을 명시하고 이메일 수신/보존 정책과 일치시킴 |
| P2 | 초대 재발급은 새 토큰이며 만료가 세션 만료와 연결 | 일정 연기·재연장 후 종이에 출력한 기존QR이 유효한지 회귀 검증 |

QR는 `#invite` 토큰을 서버에서 익명 사용자·기기에 연결된 회의 권한으로 교환한다. 일반 `/m/watch`는 6자리 코드를 요구한다. 예약 세션은 예정 시각+6시간 만료와 활성 세션 연장 경로가 있으나 영구 유효한 QR라고 표현하면 안 된다.

## 운영자 콘솔 별도 개선안

1. 회원: 가입/승인/정지, 소속, 역할, 계정 상태. 호스트 작업 공간으로 돌아가는 명확한 전환.
2. 라이선스: 유효 기간, 사용 가능한 기능, 동시 회의·연결 수, 사용량, 기본 엔진. 엔진 배정 변경은 기존 합의대로 다음 세션부터 적용.
3. 회의·장애: 회의 상태, 연결 복구, 요약 작업 상태, 오류 원인. 실제 음성·원문 지원 접근은 대상과 사유를 명시하고 기록.
4. 지원 모드: 어떤 고객의 화면을 보는지 상단에 지속 표시. 보기는 기본 읽기 전용이며 실제 변경은 별도의 명시적 행동으로 수행. 비밀번호나 개인 API 키 원문은 지원 화면에 노출하지 않는다.

이는 제안이며 이번 작업에서 권한 우회나 전 고객 데이터 공개를 추가하지 않는다.

## 참여자 흐름

- QR: 초대 권한이 포함된 주소 → 인증코드 입력 생략 → 간략 정보 및 동의 → 대기.
- 일반 링크: 입장 주소 → 인증코드 확인 → 같은 정보·동의 흐름.
- QR 자체를 스캔했다는 사실은 권한이 아니다. QR에 들어 있는 초대 주소가 권한을 전달하므로 그 주소를 복사해 열어도 같은 권한을 가진다. QR용 초대와 일반 입장 링크는 별개로 관리해야 한다.
- 정보는 이름 필수, 회사/부서 선택을 기본 제안한다. 요약 이메일을 받을 때 이메일과 수신 동의를 받는다. 현재 수집 항목·동의 계약 변경은 별도 검토 후 반영한다.
- 개인정보 안내와 회의 요약 이메일 동의를 구분한다. 요약 이메일 동의 여부를 자막·종료 기록 열람 권한으로 쓰지 않는다. 입장 화면의 마케팅 동의는 핵심 흐름에서 분리하는 것을 권장한다.
- 대기: 회의명·예약 시간·선택 언어·입장 완료 표시. 실제 회의 시작 신호가 오면 라이브로 전환.
- 라이브: 선택 언어 자막, 현재 발언자, 발언 요청, 공유와 시스템 언어. 호스트 설정·회원관리 미노출.
- 종료: 원문은 즉시 열람, 요약은 생성 상태를 별도 표시. 생성 완료 후 자동 반영. 이메일은 동의한 사람에게만 별도 전달하며 이 작업에서 실제 메일을 발송하지 않는다.

## 가장 중요한 언어 안정화

입력 언어 자동 감지와 사용자가 읽을 번역 언어는 별개다. 출력 언어 선택을 매 partial 결과에 맞춰 변경해서는 안 된다.

| 입력 | 선택 출력 | 기대 동작 |
| --- | --- | --- |
| 영어 | 한국어 | 한국어 번역 계속 표시 |
| 한국어 | 영어 | 영어 번역 계속 표시 |
| 일본어 | 한국어 | 한국어 번역 계속 표시 |
| 한국어 문장에 API·EBITDA 포함 | 영어 | 짧은 외국어 단어만으로 원문 언어·출력 역할을 뒤집지 않음 |
| 다음 확정 발화에서 한국어→영어 | 설정 언어 | 새 구간에서 자동 판정 허용 |

공식 문서 확인:

- [Soniox 언어 감지](https://soniox.com/docs/stt/concepts/language-identification): 언어 태그는 token 단위이고 실시간 문맥이 늘면서 임시 오분류나 태그 수정이 일어날 수 있다. 문장 일관성을 고려하는 모델이지만 앱의 표시 안정성은 별도 처리해야 한다.
- [Soniox endpoint](https://soniox.com/docs/stt/rt/endpoint-detection): `<end>`는 안정된 발화 구간 확정 신호다. 지나치게 공격적인 조기 확정은 정확도와 긴 발화 분할에 영향을 주므로 단순히 최저 지연 설정으로 바꾸지 않는다.
- [Gemini Live Transcribe](https://ai.google.dev/gemini-api/docs/live-api/live-transcribe): 자동 언어 감지, 수정될 수 있는 interim과 권위 있는 final transcript를 구분한다.

이에 따른 앱 설계는 ‘확인된 발화 구간의 임시 표시 언어 유지 → 상충하는 중간 결과 보류 → 최종 원문 검증 → 다음 구간 재판정’이다. 잘못 감지한 첫 단어를 무조건 고정하거나 혼합 문장을 거짓 단일 언어로 저장하지 않는다. 발화 구간 확정이 문법적인 문장 완료와 언제나 같지는 않으므로 실제 음성 검증이 필요하다.

## 요약 대기 개선

현재 발견한 UI 결함은 요약/원문 동시 요청을 함께 기다려 원문까지 늦어지고, 한정된 조회 횟수 초과를 생성 실패로 취급하는 것이다.

- 원문과 요약 결과를 독립 반영한다.
- 서버 pending/running: 생성 중 로딩과 느린 주기 확인 유지. 오래 걸리면 지연 안내.
- 조회 실패/네트워크 시간 초과: 생성 실패라고 단정하지 않음. 제한된 재조회 후 확인 지연 안내와 재확인.
- 실제 서버 생성 실패: 오류와 재생성 행동 표시. 무한 로딩으로 숨기지 않음.
- 페이지 숨김/종료 시 불필요한 조회를 쉬거나 취소하며 중복 요청을 막는다.

서버 현재 구조는 모델 시도당20초, 전체60초 제한, 조회5초 제한, DB lease5분과 종료 후 after() 실행이다. 느린 작업을 장시간 안정적으로 보장하려면 지속 작업 큐·worker·heartbeat·운영자 작업 상태가 다음 단계다. UI 로딩을 추가했다고 서버 작업 실행 보장까지 완성되는 것은 아니다.

## 검증 및 구현 상태

코드 변경·회귀 결과를 아래에 기록한다. 유료 모델 실시간 세션, 실제 계정/DB 변경, 운영 배포는 실행하지 않는다.

### 구현한 변경

- `src/subtitle-realtime.js`: 데스크톱 입력별 언어 유지, 상충 partial 보류, 최종 본문 재판정, 재연결/정지/경계 초기화, 늦은 비동기 번역의 덮어쓰기 차단.
- `media-gateway/src/sentence-language-routing.js` 및 pipeline/adapter: 라이브콜 확정 발화 구간의 임시 경로 유지. segmentId·generation으로 늦은 이전 final이 새 구간의 상태를 초기화하지 못하게 함.
- `LiveViewer.tsx`, `useHostSummaryLifecycle.ts`, `meeting-summary-polling.ts`: 원문/요약 독립 반영, 정상 pending은 최대25초 간격으로 계속 확인, 연속 조회 실패만 제한, 숨김 상태 조회 중단, 이전 요청 응답 차단.
- `ParticipantMeetingMinutes.tsx`: 종료 기본 탭 원문, AI요약 생성 중 기존 skeleton 표시. 실제 오류는 오류와 재확인으로 구분.
- `post-session-summary.ts`와 summary API: 발언 당시 프로필 이름을 현재 참여자 이름으로 바꾸던 요약 귀속 오류 수정.

구조 결정 근거: [React useEffect](https://react.dev/reference/react/useEffect)의 cleanup 규약에 따라 타이머와 요청을 종료·의존성 변경 시 정리한다. 데이터 조회 실패를 생성 작업 실패와 섞지 않는다.

### 실행한 검증

- 데스크톱 관련59개, gateway 전체625개 통과.
- 루트 전체1,511 통과,19 건너뜀,실패0. 위 데스크톱 집중 테스트는 루트 테스트에 포함되므로 별도 합산하지 않는다.
- 독립 검수: 정상pending10회에서실패종료없음, 최대동시조회1, hidden조회0, dispose후재예약0. 언어경계·재연결·음원분리검증.
- 실제 ParticipantMeetingMinutes를 모의상태와 연결해 원문기본열람→AI요약 skeleton→실제실패표시→재확인→원문유지를 브라우저에서 시연했다. 임시 페이지는 원복했다. 이 시연은 실제 LiveViewer 전체 모바일 배치나 유료 모델 생성 검증을 의미하지 않는다.
- 언어 보장 경계는 공급자가 확정한 구간이다. 문법상 긴 문장의 중간에서 공급자가 구간을 확정할 수도 있다. 이를 완전히 제거하거나 인식 정확도100%를 보장했다고 주장하지 않는다.

### 다음 검증과 우선순위

1. **P0 실음성 검증**: 영어·한국어·일본어, 약어·고유명사, 동일 발언자의 언어 전환, 다른 발언자 전환, 중첩 발화, 긴 문장, 잡음과 연결 복구를 동일 녹음으로 두 엔진에서 비교한다. 구간 안의 언어 역전 횟수, 최초 자막 지연, 최종 확정 지연, 누락 구간, 번역 방향 오류를 기록한다. 이번에는 유료 모델 호출 없이 회귀 입력으로 검증했다.
2. **P1 요약 작업 내구성**: 지속 큐와 worker, lease heartbeat, 작업별 상태와 실패 원인, 완료 알림 및 이메일 발송 작업. UI를 오래 기다리게 하는 것만으로 provider timeout 문제까지 해결하지는 않는다.
3. **P1 운영자 별도 콘솔**: 라이선스·사용량·연결 한도·엔진 배정, 지원 대상 선택과 감사 기록. 일반 호스트 화면은 캡션·Live Call·설정에 집중한다.
4. **P2 참여 입장 단순화**: 이메일 선택화와 동의 계약, 일반 링크 코드 정책, QR 일정 변경 회귀, 종료 기록 열람 기한 안내.

이번 변경은 DB·배포·회원 계정·라이선스 정책을 실제로 바꾸지 않는다. 롤백은 해당 언어 안정화와 요약 UI 코드를 이전 버전으로 되돌리고 기존 원문·프로필 이력을 보존하는 방식이다.

### 최종 검증 결과

루트1,511 + 게이트웨이625 + 웹1,107 = 총3,243개 통과. 루트19개 건너뜀, 실패0. 루트·웹 타입 검사와 변경 공백 검사 통과. 웹은 Live1,029 + Core78이다.

기록 화면도 서버가 요약 생성 중이라고 응답하는 동안25초마다 상태를 확인하고, 숨긴 화면에서는 조회를 쉰다. 참여자·호스트·기록 화면 모두 실제 실패를 정상 대기로 위장하지 않는다. 임시 브라우저 시연 페이지는 원복했으며 운영 서비스·DB·외부 이메일 발송은 변경하지 않았다.

마지막 검수에서 기록 자동 갱신이 이전 언어로 선택을 되돌리는 경합을 발견했다. 현재 선택·표시 키, 진행 중 요청, 타이머가 기억한 키를 함께 확인하도록 수정했다. 실제 effect 회귀에서 다른 언어 선택 후 이전 타이머 조회0회, 수동 요청 중 자동 조회0회, 대기 상태 복귀 후 조회1회를 확인했다.
